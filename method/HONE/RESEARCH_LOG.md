# RESEARCH_LOG.md — HONE

Hardware: 1× NVIDIA RTX 5880 Ada (49 GB), shared with an unrelated job (~13 GB);
CUDA 12.8, torch 2.11, transformers 5.5.4. Disk is tight (~58 GB free), so fold
checkpoints are deleted as soon as their candidates are written.

## 2026-09-23 — Stage 0: choosing the direction by measurement

Started from CARVE's own finding: its F1 gain over OneIE is produced entirely by a
heuristic verifier (a threshold on the mean token posterior of each span). The
question was how much a *perfect* verifier could gain over the same candidates.

Oracle-verifier ceiling over CARVE's argmax candidates (dev):

| candidate set | candidates | oracle Arg-C | + oracle type |
|---|---|---|---|
| seed 42 | 795 | 70.94 | 77.59 |
| seed 13 | 801 | 74.22 | 80.24 |
| seed 101 | 800 | 72.24 | 79.52 |
| union of 3 | 1,764 | **80.81** | 88.44 |
| union, through HONE's real decoder | 1,764 | **78.67** | — |
| CARVE frozen rule (achieved) | — | 47.14 | — |

→ ~30 points between heuristic and perfect verification over identical
candidates. HONE is built to close that gap.

Literature check: EXCEEDS (ACL 2026) evaluates on "SciEvents", a different
dataset. No newer comparable result on Dong et al. SciEvent besides CARVE.

## Stage 1: correctness

- Vendored CARVE tagger as the proposer (`hone/`), imports rewritten, benchmark
  resolved from the workspace; splits load 1278/158/163.
- `propose.py eval` reproduces the ceiling analysis exactly: 795/801/800 dev
  candidates for seeds 42/13/101; pooled union = 1,764.
- An oracle verifier through the real decoder reaches 78.67 — the pipeline can
  express the headroom.
- OOF smoke test (1 epoch): 257 held-out windows → 1,144 candidates, checkpoint
  deleted. Folds: 1021–1023 train / 255–257 held out.
- Verifier smoke test: trains, predicts, decodes, scores end to end.

Test-set hygiene note: dev **and test** candidates were generated by running the
frozen CARVE proposers (inference only, no labels). No test statistic is
computed until the single frozen evaluation.

## Stage 1b: the premise of H4, measured

Candidates the full-train proposer produces on its **own training windows**:
3,924 candidates, **97.5 % positive**. Out-of-sample dev candidates: **32.5 %**
positive (pooled). A verifier trained in-sample would see 2.5 % negatives — it
could only learn "keep everything". This is the quantitative case for
cross-fitting; H4 tests whether it matters for the final score.

## Stage 2: out-of-fold proposals (running)

15 proposer runs = 5 folds × 3 seeds, CARVE recipe, epoch selected on real dev,
each decoding its held-out fold. ~11 min/run.

### Cross-fitting reproduces the test-time candidate distribution

| candidate source (proposer seed 42) | candidates / window | positive rate |
|---|---|---|
| OOF fold 0 | 5.18 | 36.2 % |
| OOF fold 1 | 4.77 | 35.5 % |
| **dev** (full-train proposer, reference) | **5.03** | **39.6 %** |

Out-of-fold candidates match dev on both volume and error rate; in-sample

D4, before any verifier is trained.

## Stage 3: H1 — one verifier over one proposer seed

Verifier seed 42, trained on OOF candidates of proposer seed 42 (5 epochs,
DeBERTa-v3-large, effective batch 16), validated on dev candidates of the frozen
CARVE seed-42 proposer. Dev, rule tuned per run.

| | Arg-C IoU | P / R | Arg-I IoU |
|---|---|---|---|
| CARVE seed 42, tuned threshold (control) | 47.66 | — | 55.50 |
| HONE-H1 verifier (keep + role from verifier) | 47.14 | 53.3 / 42.3 | **57.91** |
| HONE-H1, hybrid role α = 0.5 | 48.93 | — | — |

**H1 as pre-registered is falsified** (−0.52 vs control). The diagnosis splits
the verifier's two jobs:

| decision | proposer | verifier |
|---|---|---|
| keep ROC-AUC (candidate matches gold) | 0.860 | **0.890** |
| role accuracy on gold-matched candidates | **81.3 %** | 77.1 % |

The verifier is a better *filter* (hence +2.4 Arg-I) but a worse *labeller*: the
tagger sees every token's role evidence during training on 1,278 windows, the
verifier sees only ~6.4k candidate spans, 64 % of which are negatives. Mixing the
two role sources (α = 0.5) recovers +1.27 Arg-C over the control — above the
pre-registered threshold on one seed, but one seed is inside CARVE's seed noise
(±0.5), so it is not yet a result. Hybrid role mixing (`select.mix_roles`,
α ∈ {0, .25, .5, .75, 1}) is now part of the frozen-rule grid.

Decoder: `any`, `iou` and exact weighted interval scheduling (`wis`) give the
same 47.14 on single-seed candidates — they only differ when candidates overlap,
which single-seed argmax spans never do.

### Error anatomy of dev negatives (proposer seed 42, 795 candidates)

| candidate class | count | share |
|---|---|---|
| fragment / boundary error of a gold span (best IoU ≤ 0.5) | 309 | 38.9 % |
| unannotated text | 145 | 18.2 % |
| matches gold, proposer role right | 256 | 32.2 % |
| matches gold, proposer role wrong | 59 | 7.4 % |
| on PrimaryObject / SecondaryObject | 21 | 2.6 % |
| on Agent / trigger | 5 | 0.6 % |

Fragments are the largest error class and no verifier can fix them by keeping or
dropping — the right span is not a candidate. Ceiling if unions of ≤ 3
consecutive candidates (gap ≤ 2 tokens) are added as candidates: 71.25 → 75.64
(single seed), 80.27 → 81.54 (pooled). → **H7 (candidate composition)**, below.

## Stage 4: H7 — candidate composition (proposer seed 42, verifier seed 42)

795 → 1,652 dev candidates (positive rate 39.6 % → 38.1 %).

| dev, same full frozen-rule grid (θ, min_len, decoder, role α, type λ) | Arg-C IoU | Arg-I IoU |
|---|---|---|
| H1 verifier, plain candidates | **49.16** (α .5, λ .25, `any`) | 57.91 |
| H7 verifier, + composed candidates | 48.82 (α 0, λ .5, `wis`) | 58.10 |
| H7, verifier-only rule (training-time tuning) | 47.08 (epoch 3) | 58.10 |

**H7 falsified** (−0.34). Composition doubles the candidate count while adding
few new positives, so the verifier must reject ~1,000 near-miss unions per 158
windows; its advantage on fragments is eaten by new false positives. The +4.4
ceiling is real but not reachable with this verifier. Not used further.
(Checkpoint deleted, D7.)

Joint type λ: +0.23 on H1 (49.16 vs 48.93), +0.3–0.5 elsewhere — small and
consistent, kept in the grid; judged at the multi-seed stage.

## Stage 11: the single frozen test evaluation (16:4x, after the freeze)

`python3 scripts/freeze_and_test.py test --runs h2_v42_p3 h2_v13_p3 h2_v101_p3 --prop_seeds 42 13 101`

| test | Arg-C IoU | Arg-I IoU | trigger ROUGE-L |
|---|---|---|---|
| verifier 42 | 53.22 (P60.9/R47.3) | 63.15 | 78.05 |
| verifier 13 | 54.02 (P58.1/R50.5) | 63.25 | 78.05 |
| verifier 101 | 51.95 (P55.6/R48.8) | 62.74 | 78.05 |
| **HONE, mean ± std** | **53.06 ± 1.04** | **63.05 ± 0.27** | **78.05** |
| CARVE (frozen, 3 seeds) | 50.48 ± 1.15 | 57.95 | 76.93 |
| OneIE (paper's best baseline) | 41.61 | 53.57 | 75.08 |

Paired window bootstrap vs CARVE (5,000 resamples, same windows for both
systems in every replicate, each side = mean of its 3 runs):

| | Δ (HONE − CARVE) | 95 % CI | P(Δ > 0) | HONE 95 % CI |
|---|---|---|---|---|
| Arg-C IoU | **+2.58** | [+0.34, +4.88] | 0.989 | [48.29, 57.70] |
| Arg-I IoU | **+5.10** | [+2.67, +7.59] | 1.000 | [58.48, 67.32] |

Both gains exclude zero. HONE's Arg-C lower bound (48.29) is 6.7 above OneIE.

ROUGE-L is identical across verifier seeds by construction: trigger and window
type come from the proposer posteriors averaged over the three seeds, not from
the verifier (type λ only changes type when role evidence disagrees). Its
+1.1 over CARVE is therefore a posterior-averaging effect, not a verifier
contribution, and is not claimed as one.

Dev → test: dev 50.93 → test 53.06 (CARVE: 47.14 → 50.48); the test set is
easier for both systems by a similar margin, so the rule did not overfit dev.

## Stage 12: component ablation and the pooled-threshold control (after test)

Each row re-freezes its free rule components on dev (max mean dev Arg-C over the
3 verifiers), then is applied once to saved test probabilities. No row was
selected on test. `scripts/ablation.py`, `scripts/pooled_threshold_control.py`.

| variant (same 3 H2 verifiers) | dev Arg-C | test Arg-C | test Arg-I |
|---|---|---|---|
| **HONE (full, frozen)** | **50.93 ± 1.23** | 53.06 ± 1.04 | 63.05 ± 0.27 |
| − hybrid role (verifier roles, α=1) | 49.44 ± 0.97 | 52.26 ± 1.83 | 63.18 ± 0.46 |
| − verifier role (proposer roles, α=0) | 50.13 ± 0.39 | 53.13 ± 0.54 | 63.18 ± 0.26 |
| − joint type (λ=0) | 49.66 ± 1.35 | 53.12 ± 0.71 | 63.76 ± 0.40 |
| pure verifier (α=1, λ=0) | 48.51 ± 0.99 | 52.26 ± 1.49 | 63.52 ± 0.20 |
| collision `iou` instead of `any` | 50.33 ± 1.27 | 52.96 ± 0.85 | 62.94 ± 0.23 |
| **no verifier**: pooled 3-seed candidates, CARVE-style threshold on `conf_max` | 48.65 | **53.87** | 62.29 |
| *CARVE (frozen, per-seed candidates)* | 47.14 ± 0.26 | 50.48 ± 1.15 | 57.95 |

(control keep scores on dev: conf 47.90, conf_max 48.65, conf·agree/3 47.05;
θ grid extended on dev only: best 48.89 at θ .96 — frozen rule unchanged.)

### What this says — stated plainly

1. **Pooling the three proposers' candidates is the dominant source of the test
   gain over CARVE.** Pooled candidates + a confidence threshold alone reach
   53.87 test Arg-C (+3.4 over CARVE), without any verifier.
2. **The verifier's advantage over that control is dev-only**: +2.3 on dev
   (50.93 vs 48.65), −0.8 on test (53.06 vs 53.87). Both differences are inside
   the ±2.3 paired sampling interval seen above, so neither sign is established.
   The verifier *does* add Arg-I (+0.8 test, +~1.5–2 dev) — it is a better filter
   of spans, not of roles.
3. The dev-selected decoding add-ons (hybrid role, joint type) each gain ~1–1.5
   on dev and ~0 on test. They are dev-fitted, not robust contributions.
4. This control was not pre-registered (H2's control was the single-seed
   verifier). It should have been run before the test evaluation; it is reported
   here as found, and nothing is re-selected on its test number.

Consequence for the claim: "HONE beats CARVE" holds (Δ +2.58, CI excludes 0),
but the *verifier* is not yet shown to be the reason. Any follow-up that tries to
make the verifier beat the pooled control must be selected on dev and reported as
a second test look.
